# ANIMO-ARCH05 coupled transaction boundary

Status: `CANDIDATE_ARCHITECTURE_DESIGN`.

## Purpose

This document defines the ownership boundary around one coupled trial without defining the future timestep acceptance algorithm.

ARCH01 already requires `AcceptedState`, `TrialState`, `TrialScratch` and `TransferJournal` separation. ARCH05 extends that concept across external hydrology and crop owners.

## Accepted generations

Before a coupled trial begins, each participating owner has one accepted generation:

- ANIMO accepted physical state;
- external hydrology accepted state;
- optional external crop accepted state.

The orchestrator binds those generations and the intended interval `[t0,t1]` into one `trial_id`.

No participant may silently substitute a newer generation under the same trial identity.

## Immutable producer frames

External owners expose immutable frames rather than mutable internal arrays. A frame may contain both accepted-start coordinates and proposed-end coordinates generated by the producer's own trial.

Every frame is pinned by a unique frame id plus producer accepted/trial snapshot ids. If any value is revised, the frame identity changes.

## ANIMO trial

ANIMO evaluates its trial using the exact bound exchange frames. The resulting object contains at least:

- candidate ANIMO trial state identity;
- typed transfer journal identity;
- realized exchange results such as crop uptake;
- diagnostics outside physical state;
- compatibility metadata tying the result to the input frame ids.

Completing this evaluation does not itself commit state.

## Coupled accept

A later qualified orchestration policy may accept the interval only when the participating trial generations are mutually compatible and all required model-specific acceptance criteria have succeeded.

Logical accept forms one commit group. The candidate requirement is atomic at the coupling level: ANIMO and external-owner generations that represent the accepted interval must agree on the same interval and transaction lineage.

ARCH05 does not require a database-style distributed transaction implementation. It requires that architecture and APIs make partial scientific commit impossible to mistake for a valid coupled accepted state.

## Coupled reject

On reject:

- ANIMO accepted physical state is unchanged;
- external hydrology accepted physical state is unchanged;
- external crop accepted physical state is unchanged;
- ANIMO trial state and transfer journal are discarded;
- unaccepted realized uptake/result messages are discarded;
- rejected physical transfers do not enter cumulative physical ledgers.

Diagnostic attempt counters may survive outside physical state if later diagnostic policy permits them.

## Retry

A retry is a new trial attempt. It may use revised producer frames or exactly equivalent values, but it receives a new `trial_id`. Immutable frame ids are never reused for mutated values.

The future TIME workunit must still determine when and how interval bounds may change on retry, how substepping is coordinated, and how coupled convergence is judged.

## No hidden side effects

Adapters and process kernels must not update external files, mutable global model objects, report accumulators or checkpoints as a side effect of trial evaluation.

Any operation that cannot be rolled back must occur only after the future orchestration contract has admitted the corresponding coupled accept.

## Result idempotence

A trial result is identified so that an orchestrator or external crop owner can detect accidental duplicate consumption. The same realized nutrient-transfer result must not be applied twice because a message was retransmitted.

This is an interface integrity requirement, not a numerical tolerance policy.

## Restart boundary

A coordinated restart starts from accepted generations only. Trial frames/results are normally ephemeral and are not portable restart state.

ANIMO's checkpoint references the external exchange/layout identities needed to verify compatibility, but it does not serialize foreign hydrology or crop physical state.

## Gate boundary

This model is deliberately weaker than a canonical TIME/exchange implementation. It specifies what must be atomic and traceable, but not the algorithm that decides acceptance, iteration count, timestep size or convergence. Those remain serial qualification tasks after the required migration baseline gates.
